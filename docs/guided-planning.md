# Guided deployment planning

Selecting “Plan deployment with the assistant” calls the native `planning_questions` command. The configured AI provider receives the deterministic project analysis (service evidence, required environment key names and volume metadata), not `.env` values. It returns up to six validated questions using a function tool. The prompt requests two to five everyday questions about intended use, audience, uploads/file size/retention where applicable, and budget when useful. Questions and hints follow the interface language. Users may choose or write that they are unsure.

Answers are passed through `PlanChoices.answers` to the existing bounded agent planning loop. The agent can inspect non-secret project snippets and recommend live plan/bundle IDs and per-volume copy or persistent-disk settings. It explains storage headroom and resource assumptions in its rationale. The Rust planner applies these recommendations only in guided mode, gives explicit user choices priority, and validates the resulting platform, available plan, disk name/size, mount scope and dependency graph. It never automatically selects temporary storage. No performance capacity is guaranteed by an audience estimate.

The default review shows a plain-language recommendation, saved-file allocations, the estimate, and a deploy button that opens the existing concrete approval dialog. “Change deployment settings” expands the existing service/network/environment controls with the proposed choices already selected. Returning to the simple view regenerates a dirty plan. Warnings are expandable; genuine blockers remain visible and prevent deployment. Missing secrets still require entry. Shared persistent volumes across applications are blocked in guided mode because separate Liara disks cannot preserve cross-app sharing. This feature does not migrate data or redesign such applications automatically.

Persistent disk fees are still explicitly excluded from the displayed estimate where no verified price contract is available; the UI does not claim an all-inclusive total. Provisioning and deployments still require approval tied to the exact revision.

## Editable automatic environment settings

The agent may suggest non-secret defaults for declared environment keys. The backend discards suggestions for keys that look like credentials, and generates application signing secrets locally (including framework-specific Laravel application keys). Values remain in the native session, are loaded into editable fields, and are never stored in plan JSON or sent back to the model. Local `.env` values and existing resource values take precedence over suggestions. Managed database fields are linked automatically, including PostgreSQL environment names; an explicit user-entered value overrides an automatic connection binding. Third-party API keys and credentials without a known value remain required inputs.

Guided planning now fills unresolved saved volume choices rather than allowing blank old entries to mask agent recommendations. If no estimate is supplied, a disclosed 10 GB starting allocation is used for persistent runtime data. Missing configuration files and shared persistent folders still need review. The simple view explains this in a plain readiness notice; the detailed technical blocker list is available in deployment settings. Neither view allows an unresolved setup to be deployed.

All select controls now use a themed accessible combobox/listbox with arrow, Home/End, Enter, Escape, type-ahead and outside-click handling, including within modal dialogs. The review heading uses a short localized description spanning the workspace width.

## Automatic shared-file Django/Nginx recipe

Before the AI recommends resources, guided planning recognizes a bounded Django + Nginx Compose pattern and groups the proxy with the web process. PostgreSQL remains a managed resource. This preserves shared media/static paths inside one application rather than suggesting independent disks for data that must be shared.

The initial recipe supports one root-context Django application based on a single-stage Debian Python image with `/app` as its working directory, `COPY . .`, a JSON application command on port 8000, and an optional forwarding shell entrypoint. The local Nginx front end must use standard 80/443 listeners, a checked read-only configuration, and mounts that map to application disks or included immutable assets. Unsupported patterns keep their review blockers. No claim is made that arbitrary Compose topologies can be consolidated.

Only the staging snapshot changes. The generated Dockerfile installs Nginx, preserves the original entrypoint (including migration/collectstatic behavior), and starts a fixed process supervisor. Nginx listens on 8080 and proxies locally to the application's existing 8000 listener. The supervisor validates Nginx configuration and stops both process groups when either process fails or a stop signal arrives. Runtime temporary files go under `/tmp`.

The recipe rewrites media/static aliases to the application's disk paths, keeps immutable partner assets, replaces the internal upstream with loopback, removes container certificate directives and Certbot challenge handlers, and removes the local HTTPS redirect that would loop behind edge TLS. Business-specific host routing remains. Custom domains still need to be attached to the combined app through the domain workflow; TLS is handled at Liara's edge. Existing local database/media data is not automatically migrated, and previously provisioned resources are not deleted.

The consolidated topology and generated files are available in deployment settings; the approval explicitly lists running the web app and Nginx together. A new plan/revision is required for this topology change. Resuming an old approved topology does not silently replace it.

Validation: normal Rust tests cover grouping, shared paths, unchanged source, unsupported base images and command quoting. `python3 scripts/check-grouped-runner.py` checks failure propagation and graceful shutdown with harmless child processes. An opt-in read-only project check is available with `LIARA_RECIPE_PROJECT=/path/to/project cargo test --manifest-path src-tauri/Cargo.toml recipes::tests::real_project_recipe_check -- --ignored`. `LIARA_RECIPE_EXPORT` optionally exports generated configuration for isolated Nginx syntax/routing checks. The `/p/shop` recipe and isolated media/static/partner-asset routes were checked locally; no live Liara deployment was performed.

When this grouping replaces a partially deployed topology, matching live resources previously recorded for the same account/team, project folder, service ID, name and platform are preselected for reuse. The concrete review/approval still identifies them as existing resources. A different explicit resource choice or new name is preserved; no resource is reused solely because its name happens to match. The old separate proxy, if provisioned earlier, remains untouched and may still cost money until the user removes it in Liara. Django host/origin environment suggestions preserve existing entries while adding the combined app's Liara URL; these values remain editable.

Release requests now explicitly carry the approved persistent disk mount list (`name` and `mountTo`), as in the official CLI release contract, so provisioned disks are attached to the combined application. Invalid AI suggestions to copy named runtime volumes into an image are normalized to persistent storage in guided mode; explicit unsupported manual choices remain reviewable blockers.

## Release submission failures and recovery

Source releases include the official CLI's default `build: {cache: true}`, an empty `platformConfig` when no platform-specific options are configured, and honest empty Git metadata for the staging copy. Environment variables remain an object and persistent disk mounts accompany the release. These fields are corroborated by the CLI implementation; the published OpenAPI release request schema is incomplete.

HTTP 500 is not treated as a definite rejection and never triggers an automatic POST retry. For a failed submission at least one minute old, Resume can offer an explicit retry only when the app has the existing resource/source identifiers, no release identifier, and Liara's release history explicitly reports both `total: 0` and an empty release list. The approval names this retry. The backend checks the same history again after approval, before clearing the uncertain request flag. Nonempty or unrecognized history blocks resubmission rather than guessing which release belongs to the run. Existing resources and the uploaded source are reused; accepted builds with saved release IDs continue normal polling.

Server errors retain recognized message/error text, redact secrets, and report when Liara supplies no details. Arbitrary response JSON/HTML is not dumped into logs. A read-only diagnostic is available via `LIARA_INSPECT_RUN_ID=<saved-run-id> cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --features desktop liara::live_diagnostics::inspect_saved_run_releases -- --ignored --nocapture`; it uses the desktop's saved Secret Service connection and checks the account/team context before listing release states. It never submits releases. On 2026-10-23 the failed `/p/shop` run's `shop-web` history returned zero releases. This establishes that no release was listed at that time, but does not prove why the earlier HTTP 500 occurred. The corrected request has not been deployed live from development tools.

## Approved changes to original project files

Failures and blocked plans expose **Review a project fix with the assistant**. For application failures, the agent can read scoped, redacted project snippets and propose up to eight edits to existing UTF-8 text files (64 KB each). It is instructed to use this only when staged deployment configuration cannot solve the evidenced problem. For API, network and quota errors, the backend returns an explanation without proposing source edits.

The proposed edits are held in native session memory. The review modal shows each path, reason, original text and replacement, with explicit approval or cancellation. The backend binds the review to the account, plan revision and a 15-minute expiry, consumes it once, and compares each original file again before writing anything. Credential/ignored files, binary data, symlinks, path traversal and out-of-folder targets are rejected. It never runs model-generated local commands. Existing unrelated user edits are preserved. This initial workflow supports replacement of existing text files; new/deleted files are not supported.

Before applying approved edits, originals are backed up under the app data directory's `project-backups/<review-id>/`. `paths.json` maps the indexed `.original` files to their project-relative paths. Backups have private permissions; replacement files retain their original Unix mode. Writes use prepared sibling temporary files and atomic replacement per file, with rollback attempted if a replacement fails. A process or machine crash during a multi-file apply can still leave a partially applied batch; backups remain for recovery. No automatic live deployment follows a partial file-application error.

After a successful apply, a fresh deployment plan is built from the modified project. Existing run resource IDs, names, network, environment bindings and disk choices are passed through for reuse. The resulting cloud resource/cost approval is shown before submitting the new deployment. If planning, environment requirements or blockers still need attention, the user stays on review. Source-edit approval never grants blanket permission for later resource or price changes.

## Disk capacity and `not_enough_storage_space`

Liara [documents](https://docs.liara.ir/paas/disks/create/) that disks use the app's reservable storage and that insufficient capacity requires reviewing allocations or upgrading the plan. Disk sizes are not treated as an unrelated, unlimited purchase. Planning totals the requested disk allocations by disk name. Guided planning recommends a compatible larger plan when the combined allocations do not fit, including existing apps selected for reuse. For existing apps it preserves compute capacity, region and bundle, shows the old and new monthly estimate, and adds an explicit plan upgrade to the approved revision. A manually selected undersized plan remains blocked. Existing apps are upgraded only after this cost/action approval.

Before disk mutations, the executor checks the current app `planID` against the current account catalog's `volume` and totals the union of existing and requested disks. Existing disks not mentioned by the plan still count, while a reused disk is counted once. Unrecognized disk data stops the operation rather than assuming free space. If the provider returns `HTTP 400 ... not_enough_storage_space`, the request is treated as rejected, clearing its pending flag; network/server failures retain the uncertain request guard. Older saved runs with this definite rejection are reconciled on resume.

The localized recovery modal automatically prepares a recommendation from the live catalog, explains the storage requirement in everyday language, and shows the chosen plan capacity and monthly cost. The user reviews the recommendation and approves the plan upgrade; the app applies it and continues the same saved run. Resume from history also prepares this recovery when the latest error was insufficient storage. The console is a fallback if no compatible priced plan can be verified. The app never shrinks/deletes existing disks or moves uploads into ephemeral storage to make a plan fit. A read-only check on 2026-10-23 confirmed the latest `/p/shop` run has a 5 GB `small-g2` app, an existing 5 GB `shop-media` disk, and an additional approved 2 GB `shop-staticfiles` request. The required total is 7 GB; no releases were listed. No cloud mutations or original `/p/shop` edits were performed during this implementation.


Storage recovery chooses the lowest-priced available plan that fits the union of all existing/requested disks while preserving at least the current CPU/RAM, region, and feature bundle. It reuses the existing resource IDs and approved source snapshot. A recovery proposal is bound to its original run revision and saved state; approval is invalid if the run changes. Before mutations, target availability, storage and pricing are checked again. Plan resize uses the documented `POST /v1/projects/{name}/resize` with `{planID}`. A pending resize is persisted before submitting; on interruption the app reconciles `project.planID` before proceeding and never blindly resubmits an uncertain resize. No disk shrinking/deletion, ephemeral fallback, bundle change or cloud mutation occurs while displaying the recommendation.


Previously recommended plan IDs are kept as suggestions, not manual constraints. Only an explicit plan selection in deployment settings sets `planLocked`; guided replanning may replace an unlocked suggestion when workload or storage requirements change. This preserves technical users' deliberate choices while keeping the normal flow automatic. Validation covers a cached 5 GB suggestion with a 7 GB requirement, an explicit undersized override, compatible plan selection, approved existing-app upgrades and uncertain resize reconciliation. The Persian recovery UI was exercised with mocked responses. Live recommendation/upgrade verification requires a connected account; the optional read-only check could not run during the final pass because the saved Secret Service token was unavailable. No live resize was submitted.
