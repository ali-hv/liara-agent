## Evidence and scope

This catalog is generated from the complete reachable documentation crawl and linked OpenAPI specifications. An API operation is documented, not authenticated/live-tested. An asterisk on an input means the specification marks it required. Unspecified schemas are not guarantees of empty responses. All raw pages, hashes, retrieval times and failures are retained in the crawl manifest and local snapshot.

The desktop release uses account/billing, PaaS, DBaaS, object storage and DNS for deployment. Reports are limited to deployment diagnostics. VPS, mail administration, AI services, file-browser administration and ongoing SRE are cataloged but outside this release. No endpoint has been invented.

## Authentication and limitations

Send the user token using the documented Bearer Authorization scheme. For a team context, include the optional `teamID` query parameter on every API request; the app exposes this as an optional Team ID on connection, and keeps it out of model context. This is described in the [Liara API overview](https://docs.liara.ir/references/api/about/). Service base URLs differ and are recorded in liara-operations.json. Respect permissions, errors and rate limits; no numeric rate limit is assumed. Pricing and resource availability must come from current account data. Never log account/storage credential fields. Some OpenAPI schemas omit fields used by the official CLI; these must be separately corroborated before use.

### Team balance selection

The documented [`MeResponse.team.balance`](https://developers.liara.ir/spec/me.yaml) supplies the selected team's balance. `/v1/billing` documents `user.balance` for the personal user. The desktop app selects `team.balance` in team mode and never substitutes personal credit when the team balance is absent; personal mode uses `/v1/billing` as before. This normalization is covered by fixtures with different personal/team balances, zero team credit, and missing team billing data.

### Deployment request audit against the official CLI

The desktop app's project detail lookup uses the application name (`project_id`), as in [`commands/deploy.ts`](https://github.com/liara-cloud/cli/blob/master/src/commands/deploy.ts), rather than the internal MongoDB `_id`. Source upload and release submission follow the CLI's multipart `file` upload and `sourceID`/`image` release routes. Disk listing continues to use the project ID as corroborated by the CLI's `commands/init.ts`. Failed API requests include their method and path, omitting query parameters (including Team ID).

Local `.env` values are read through an account-scoped `plan_environment` native command for the reviewed plan, filtered to its required unbound keys. They are editable in memory, never stored with the plan or sent to the AI provider. Approval preserves explicit user edits, including empty values, rather than silently replacing them from disk.

### Resuming environments

Resume now opens the approval dialog directly. The native backend recovers required environment values from the run's in-memory session cache, then the existing application's Liara environment, then the project's `.env` file. Explicit edits take precedence. Fully verified applications do not require environment values again. Secret values remain outside SQLite and model context; disconnecting, switching account context, or quitting clears the session cache. Only genuinely unavailable required values return the user to the environment form.

### Source release request parity (2026-10-23)

The [official CLI deploy implementation](https://github.com/liara-cloud/cli/blob/master/src/commands/deploy.ts) sends a `build` object (cache enabled by default), object-valued `envs`, disk mounts, and, for uploaded sources, `gitInfo` and `platformConfig` in addition to `sourceID`, `port`, `type`, and the release message. These extra fields are CLI-corroborated, not fully specified by the published OpenAPI schema. The desktop now sends the corresponding default build/platform options. It excludes Git internals from the archive and uses null Git fields/empty tags instead of inventing metadata.

Release history is documented as `{total, releases, ...}`. Resume after an uncertain HTTP 500 can request explicit retry approval only after an explicitly empty history, and rechecks it immediately before submission. Existing list entries cannot reliably be attributed to a source archive using the documented list schema, so a nonempty history prevents this recovery path. No undocumented release idempotency header or source lookup endpoint is assumed.

### Disk storage allocation (2026-10-23)

[Disk creation guidance](https://docs.liara.ir/paas/disks/create/) explicitly requires available reservable storage and suggests reviewing disk allocations or upgrading the app plan when it is insufficient. The documented app detail `planID`, account catalog `plans.projects[planID].volume`, and disk-list `name`/`size` fields are used to preflight total allocations. Existing disks count toward the total even when they are not mounted by the proposed release. Guided recommendations select sufficient plans for new apps and propose explicit upgrades for existing apps. Storage recovery reads live allocations/catalogs, preserves CPU/RAM, region and bundle, and selects the cheapest compatible sufficient plan. The documented `POST /v1/projects/{name}/resize` request (`{planID}`) is sent only after approval of the exact recommendation and cost. The executor checks price/availability again and reconciles the live `planID` after interruption rather than automatically repeating the mutation. The [plan-change guidance](https://docs.liara.ir/paas/details/change-plan/) also requires that a target plan fit existing disks.

The observed disk-creation response `HTTP 400` with message `not_enough_storage_space` is classified as a definite rejection for recovery; timeouts and server errors retain an uncertain result. This observed error code is not assumed to be a complete documented error contract.
